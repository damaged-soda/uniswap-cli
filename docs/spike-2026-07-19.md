# 数据源 spike — 2026-07-19

## 目的

验证 Ethereum mainnet v2/v3/v4 的官方 schema、The Graph 鉴权边界、RPC archive/log 能力，
并为第一条 vertical slice 选择实现语言和 provider 行为。

## 上游版本

本次直接检查了官方仓库 `main`：

| 仓库 | commit |
|---|---|
| `Uniswap/v2-subgraph` | `468ce7beca3888a927f64d1f2481e59b8fded299` |
| `Uniswap/v3-subgraph` | `0f8631d0c87a0c5caee8b1d68d8f7ac42d6941d3` |
| `Uniswap/v4-subgraph` | `5c9cd2b94b8e3e5b9318de0abe09b4cdaa0ce9a3` |
| `Uniswap/v4-core` | `46c6834698c48bc4a463a86d8420f4eb1d7f3b75` |

核对结果：

- v2 schema 提供 Pair、Swap、PairHourData、PairDayData，但 pool 级 series 没有 OHLC。
- v3/v4 schema 提供 Pool、Swap、PoolHourData、PoolDayData，后两者包含 open/high/low/close。
- v4 Swap 没有 recipient；Pool ID 是 bytes32，且事件来自 PoolManager。
- v2/v3/v4 schema 的公共字段足以形成统一 pool、swap 和 series 模型，但不能抹掉版本差异。

## The Graph gateway

对官方文档列出的 Ethereum v3 subgraph ID 发起不带 key 的 `_meta` 查询：HTTP 状态是 200，
响应体为 GraphQL `errors: auth error: missing authorization header`。因此：

- HTTP 200 不能被当成查询成功；必须检查 GraphQL `errors`。
- 内置 deployment 使用 `UNISWAP_THE_GRAPH_API_KEY`。
- 自部署或第三方 deployment 走显式 URL/Bearer 配置。
- 本次没有可用 The Graph key，live subgraph 查询未冒充通过；GraphQL shape 由官方 schema +
  固定 fixture 契约测试覆盖。

## Ethereum RPC

在 personal namespace 已有的 `RPC_URL_1` 上验证：

- `eth_chainId` 返回 1。
- `eth_getBlockByNumber(12369621)` 成功，证明该 endpoint 能读 2021 年历史块。
- 对 v3 USDC/WETH 0.05% pool `0x88e6…5640` 查询连续 10 个近期区块，得到 4 条 Swap 日志。
- 同一次 25 区块请求被免费档拒绝，并明确限制为每次最多 10 个区块。
- 代表性请求延迟约 0.4 秒。
- v3 Swap topic 经节点 `web3_sha3` 核对为
  `0xc42079f94a6350d7e6235f29174924f928cc2ac818eb64fed8004e115fbcca67`。

实现据此加入：区块范围自适应缩小、总请求数安全阈值、cursor 分页、block timestamp 缓存、
v2/v3 ABI 解码、archive/chain-id doctor，以及任何失败都不输出 RPC URL。

## 语言与 vertical slice

选择 Python 3.11+、`httpx`、标准库 `argparse`：

- 与现有 Pendle/Polymarket 本地 CLI 和测试环境一致。
- 无 MCP runtime 依赖，安装后只有 `uniswap` 一个入口。
- `httpx.MockTransport` 足以固定 provider 契约；live test 单独标记。

第一条 vertical slice 是 Ethereum v3：RPC health → raw logs → 规范化 swaps。随后用相同公共
模型覆盖 v2/v3/v4 subgraph pools/swaps/series。
